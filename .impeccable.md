# e& Egypt Assistant Design Context

## Design Context

### Users

The product is for actual e& Egypt customers using an English-language support interface, primarily on phones and secondarily on desktop browsers.

Customers arrive with a concrete product question: they want to understand or compare mobile plans, internet services, prepaid systems, DataLine, Emerald, Hekaya Internet, or Hekaya Mixat. They may be uncertain, impatient, or worried about choosing the wrong product. The interface must help them ask a question immediately, understand the answer, and verify which e& product guides support it.

This is a product-information assistant. It cannot access personal accounts, complete account changes, receive passwords or verification codes, or replace official support for account-specific issues.

### Brand Personality

The brand personality is:

- **Warm:** Use friendly, human language without jokes or forced enthusiasm.
- **Reassuring:** Clearly explain what is happening, where information came from, and how to recover from errors.
- **Competent:** Keep answers and controls concise, predictable, and visibly grounded in e& product information.

The emotional goal is quiet confidence. Customers should feel that the assistant is easy to use and honest about its limits.

### Aesthetic Direction

Use the current ChatGPT chat interface as the interaction and layout reference, but do not create an OpenAI-branded clone. Reproduce the useful structural decisions in an e& visual language:

- A calm, low-contrast application shell.
- A collapsible conversation sidebar.
- A narrow centered reading column.
- Right-aligned customer bubbles and unboxed assistant responses.
- A persistent rounded composer that remains the main interaction.
- Minimal controls that appear when relevant.
- A mobile drawer and compact mobile header.

Use e& branding through the logo, exact brand-red accent, warm-tinted neutral colors, product-specific copy, focus indicators, and the send action. Do not fill large surfaces with red, repeat the logo in every message, or imitate ChatGPT's brand name, model selector, icons, or unavailable tools.

Light mode is the default customer experience. Preserve the existing dark and system options, but ensure both themes use the same hierarchy and pass WCAG 2.2 AA.

### Design Principles

1. **Conversation is the product.** Keep the message flow and composer visually dominant. Secondary navigation must recede.
2. **Familiar interaction, e& identity.** Use ChatGPT's proven chat structure while making brand expression unmistakably e&.
3. **Trust is visible.** Explain when product guides were used, show readable sources, and distinguish no-match results from technical failures.
4. **Progressive disclosure.** Start with a question field and a small set of prompts; reveal history actions, help, sources, and additional topics only when needed.
5. **Recovery over punishment.** Preserve questions, allow retry, offer undo for deletion, and never expose technical errors.
6. **Mobile is a complete experience.** Do not hide essential history, source, retry, or composer functionality on small screens.
7. **Native before custom.** Use semantic HTML, CSS, browser storage, Clipboard, `<details>`, and existing React state before adding dependencies.

## ChatGPT Interface Translation Guide

This section is the concrete design reference for future Impeccable design passes. “ChatGPT-like” must be interpreted through the details below rather than as a vague style label.

### 1. Application shell

#### Desktop

- Use a two-region full-height shell: a roughly 256px sidebar and a flexible main conversation area.
- The sidebar should use a slightly darker or more tinted neutral than the main canvas, not the current near-black block in light mode.
- Allow the sidebar to collapse completely. Do not build a permanent icon rail unless a real secondary navigation need appears.
- The main area should have a small, quiet top bar and a scrollable conversation region.
- Keep the content lane centered at approximately 720–768px. Long answers must not stretch across the entire viewport.
- The composer aligns to the same content-lane width so message text and input share one visual axis.

#### Mobile

- Replace the desktop sidebar with an overlay drawer occupying approximately 85–90% of the viewport width, capped near 320px.
- Use a compact top bar with a menu control, the title “e& Egypt Assistant,” and a new-chat control.
- The drawer must be absent from the accessibility tree while closed, close on Escape and backdrop activation, and return focus to the menu button.
- Keep the composer pinned above the safe area. The final answer and sources must remain scrollable above it.

### 2. Sidebar anatomy

- Start with a compact e& brand row: a small logo and “e& Egypt Assistant.” Do not include a long subtitle in the permanent top area.
- Place “New chat” near the top as the clearest sidebar action. Use a quiet row/button treatment rather than a full-width red slab.
- Add conversation search only if the implementation supports it; do not show a decorative search control.
- Group saved conversations by time when timestamps exist: “Today,” “Previous 7 days,” and “Older.”
- Conversation rows are single-line, truncated, and low contrast until hovered, focused, or active.
- The active conversation uses a subtle warm-neutral fill. Do not use a thick colored side stripe.
- Put rename/delete actions in a trailing overflow control. If only deletion exists in the first implementation, show a small trailing delete action on the active row and on hover/focus.
- Keep appearance, clear-history, and “About this assistant” actions at the bottom. Do not imitate ChatGPT's account/profile row when this product has no account system.

### 3. Top bar

- Keep the top bar approximately 52–60px high.
- Use “e& Egypt Assistant” as the primary label. A short secondary label such as “Product information” may appear only when space allows.
- Do not reproduce ChatGPT's model selector because customers are choosing e& products, not AI models.
- Avoid a decorative status dot. If trust context is needed, use readable text such as “Answers from e& product guides.”
- Use borders and shadows sparingly. The top bar can blend into the canvas with a single subtle bottom divider only when it improves separation.

### 4. New-conversation state

- Center the initial task vertically around the upper-middle portion of the available main area, as ChatGPT does, rather than building a marketing hero.
- Use one compact e& mark, approximately 32–44px, followed by the headline “What can we help with today?”
- Place the composer directly below the headline so typing remains the obvious first action.
- Place four low-emphasis prompt suggestions below the composer in a two-column layout on desktop and one column on narrow mobile screens.
- Suggestions should be concise customer jobs, not document titles:
  - “Compare mobile and data plans”
  - “Find an internet package”
  - “Understand prepaid options”
  - “Tell me about Emerald or Hekaya”
- Suggestion surfaces should be flatter and quieter than the composer: a subtle border or tinted fill, medium radius, no floating shadow, no large icon tile.
- Do not repeat the logo in the sidebar, top bar, and large center treatment simultaneously. Prefer sidebar plus one small empty-state mark.

### 5. Conversation column

- Use a single centered column approximately 720–768px wide.
- Keep vertical rhythm generous: approximately 24–32px between turns and tighter spacing within a single answer.
- Customer messages appear in right-aligned neutral bubbles with a maximum width around 70–75% of the conversation lane.
- Assistant answers appear unboxed on the main canvas. Do not wrap every answer in a card or full-width tinted panel.
- Do not place a large e& avatar beside every assistant paragraph. If role identification is needed, use a small “e& Assistant” label or a compact brand mark at the start of the response.
- Body text should remain around 15–16px with roughly 1.6 line height and no more than 65–75 characters per line.
- Preserve whitespace and lists generated by the assistant. Links, source labels, headings, and inline emphasis must be visibly distinct without turning the answer into a card collection.

### 6. Assistant response actions

- Place a quiet action row immediately below completed assistant responses.
- Include only actions the product actually supports:
  - Copy answer.
  - Retry after an error.
  - Regenerate only if it can be implemented without duplicating conversation history.
- Do not add thumbs-up/down controls unless feedback is stored and used.
- On pointer devices, secondary actions may become stronger on hover or focus; on touch devices, essential actions must remain visible.
- Use small monochrome outline icons with text alternatives and 44px touch targets where appropriate.

### 7. Sources

- Sources belong inside the assistant turn, directly after the answer and before the action row.
- Use a compact collapsable “Sources” disclosure or short list rather than bright pills scattered below the message.
- Each source must show a customer-readable title and page number, for example “DataLine — page 3.”
- Do not make a source appear clickable unless the PDF or page can safely be opened.
- Grounded answers show sources. Direct conversational replies do not show an empty source container. No-match replies explain that no reliable source was found.

### 8. Composer

- Treat the composer as the most important control and match ChatGPT's compact rounded geometry without copying unavailable tools.
- Use a single rounded surface aligned to the conversation width, with a subtle border or warm-neutral fill.
- The textarea grows from one line to a practical maximum height, then scrolls internally.
- Use the placeholder “Ask about e& plans and services.” A persistent accessible label must still exist.
- Place the circular send control at the lower-right edge of the composer. Use e& red for the enabled state and a neutral disabled state.
- Do not show attachment, microphone, voice, tools, or model controls unless those features are functional.
- Enter sends and Shift+Enter inserts a line break. Present this hint subtly without crowding the composer.
- During a request, prevent duplicate submission and show an honest status such as “Searching e& product guides…”. Do not fake token streaming if the backend returns complete responses.
- In an active conversation, keep the composer sticky at the bottom with a subtle canvas-colored fade behind it so messages do not visually collide with the input.

### 9. Loading, empty, no-match, and error states

- Loading should remain in the assistant message position so the conversation does not jump when the answer arrives.
- Use a restrained animated indicator and text; animation must stop under `prefers-reduced-motion`.
- A no-match response uses normal assistant-message styling, plain language, and 2–3 relevant follow-up suggestions.
- A technical error also stays in the conversation flow, explains that the question was preserved, and provides “Try again.”
- Do not use centered error pages or modal alerts for message-level failures.
- Announce loading with `role="status"`, failures with `role="alert"`, and new answers through a polite live region.

### 10. Scrolling behavior

- The message region owns vertical scrolling while the app shell remains full height.
- Scroll to a newly submitted customer message.
- Auto-scroll to an arriving response only if the customer is already near the bottom.
- If they are reading older content, preserve their position and show “Jump to latest” above the composer.
- Use immediate scrolling when reduced motion is requested.

### 11. Color and branding

- Use the current e& red (`#e63425`) as the primary brand accent unless an official brand token replaces it.
- Use red for the logo, enabled send button, selected high-value action, and focus/error cues where semantically appropriate.
- Do not use red as the main sidebar background in light mode, as a large message background, or as ordinary body-text color.
- Use warm-tinted off-white and charcoal neutrals rather than pure white and black.
- Light mode should resemble ChatGPT's quiet neutral hierarchy: subtle sidebar separation, low-contrast borders, and a clean main reading surface.
- Dark mode should invert the neutral hierarchy while keeping red controlled and readable; no red glow, glassmorphism, or neon treatment.
- Maintain at least WCAG AA contrast for text and interactive controls.

### 12. Typography

- Match ChatGPT's restrained typography hierarchy, not its exact font identity.
- Prefer the official e& digital typeface if one is available and licensed.
- If no official typeface is available, choose a readable, non-generic sans-serif pairing after reviewing actual font catalogs. Do not keep Space Grotesk merely because it is already present.
- Use few sizes: compact labels, 15–16px body, a modest empty-state heading, and no oversized marketing headline.
- Structural UI should remain regular or medium weight; reserve bold weight for the empty-state headline and essential labels.

### 13. Shape, borders, and elevation

- Composer: large continuous radius, visually similar to a pill but able to grow vertically.
- Customer bubble: soft radius with one slightly tighter corner if desired, without a shadow.
- Sidebar rows: modest 8–10px radius.
- Suggestion prompts: medium 12–16px radius, subtle border or fill, no floating shadow.
- Avoid cards around ordinary messages, nested cards, colored side stripes, gradient text, decorative glows, and blurred glass surfaces.
- Use elevation only for the mobile drawer, overflow menu, undo toast, and sticky-composer separation.

### 14. Motion

- Sidebar and drawer transitions: approximately 180–220ms using transform and opacity.
- Hover/focus feedback: approximately 120–180ms.
- New message/status transitions should use opacity and small vertical translation only.
- No bounce, elastic easing, or layout-property animation.
- Provide an equivalent immediate state change under reduced motion.

### 15. Responsive checkpoints

- 320px: no horizontal scroll; single-column suggestions; compact header; 44px controls.
- 390px: complete mobile chat with drawer, sources, retry, and safe-area composer.
- 768px: transition between overlay drawer and desktop sidebar without losing controls.
- 1024px: centered conversation lane with comfortable sidebar-to-content balance.
- 1440px and above: maintain the narrow reading lane; do not stretch messages to fill empty space.
- 200% zoom: preserve order, focus visibility, and access to the composer and drawer controls.

## Reference Basis

The reference is based on the current public ChatGPT interaction patterns and official OpenAI UI guidance available when this context was written. Durable principles include keeping content in the conversational flow, preserving the composer, using restrained system-like colors and spacing, limiting actions, and allowing partner branding through controlled accents rather than replacing the host interface hierarchy.

- [OpenAI UI guidelines](https://developers.openai.com/apps-sdk/concepts/ui-guidelines/)
- [OpenAI guidance for adding UI to ChatGPT](https://developers.openai.com/apps-sdk/build/chatgpt-ui/)

This project must not import `@openai/apps-sdk-ui`; it is not a ChatGPT plugin and does not need that dependency. Reproduce the relevant interaction principles with the existing React and CSS stack.
